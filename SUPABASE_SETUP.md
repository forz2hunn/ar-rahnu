# Supabase setup

1. In the Supabase SQL Editor for project `zyikvjbnroicbeezpxvx`, run [`supabase/schema.sql`](./supabase/schema.sql). It creates the per-user data table, enables row-level security, and adds the table to Realtime.
2. Run [`supabase/audit-trail.sql`](./supabase/audit-trail.sql) in the same project to enable append-only, SHA-256 hash-chained records for portfolio, organization, and membership inserts, updates, and deletes. The file also installs a per-record trigger that writes one audit event for every transaction, asset, institution, supplier and Surat Akuan Gadaian (SAG) document that is created, changed or removed, including the actor identity (`actor_user_id`, `actor_email`, `actor_display_name`), the database timestamp, the record label/type and the changed field names in `context`. It exposes the `ar_rahnu_record_activity` RPC that the app uses to record sign-in, sign-out, password, profile and export activities, and it groups every organization member's activity into the organization chain so managers see one complete trail. Summary columns (`occurred_at_utc`, `actor_email`, `action`, `context`, `source_ip`, `user_agent`, …) let the Audit Trail list and its row-level security filters read events without decompressing the large before/after payloads, which prevents `canceling statement due to statement timeout` on portfolios with heavy history; the full payload is loaded only when an event is opened. The summary columns are plain columns filled by an insert trigger, and existing events are backfilled in small batches during the migration. If the migration has not been applied, the page falls back to a limited compatibility mode instead of failing. **Audit events are retained for 24 hours only**: `ar_rahnu_prune_audit_events()` deletes older rows and is scheduled every 15 minutes with `pg_cron`; run `select public.ar_rahnu_prune_audit_events();` manually if `pg_cron` is unavailable. Chain verification is anchored at the earliest retained event, so export any evidence before it expires. Rerun the whole file after changes so the updated functions, columns and triggers are installed. The Audit Trail page is available to Admin and Manager accounts. Redeploy the updated `user-admin` Edge Function as described in [`supabase/USER-MANAGEMENT.md`](./supabase/USER-MANAGEMENT.md) so administrative account actions include actor/session metadata and audit events.
3. Run [`supabase/portfolio-relations.sql`](./supabase/portfolio-relations.sql) to backfill relational records and install foreign keys and automatic synchronization. It must run after `schema.sql`.
4. Run [`supabase/transaction-attachments.sql`](./supabase/transaction-attachments.sql) to create the private bucket and access policies for SAG support documents. It must run after `schema.sql`. Each SAG accepts up to seven files, with a 50 MB limit per file.
5. Run [`supabase/profile-photos.sql`](./supabase/profile-photos.sql) to create the private bucket and access policies for member profile photos. Each user can only read, upload, replace and delete files inside their own `auth.uid()` folder.
6. Copy `.env.example` to `.env.local` and set `VITE_SUPABASE_ANON_KEY` to the project's publishable key (or legacy anon key). The project URL is already filled in. Never use a `service_role` or secret key in this browser app. Run `npm run check:keys` to verify the keys without printing their values: the publishable key is valid when the REST probe returns `permission denied for table ar_rahnu_organizations` (RLS rejecting the anonymous role is expected), while `Unregistered API key` means the key was rotated. `SUPABASE_SECRET_KEY` in `.env` is optional local/CLI tooling only — the browser app never reads it, so an outdated secret does not break the app.
7. Restart the Vite server, open the app, and register/log in with Supabase Auth. If email confirmation is enabled, confirm the account before logging in.
8. The first login imports the existing browser's transactions, institutions, assets and suppliers only when that account has no cloud data yet. If cloud data already exists, it is loaded as the source of truth.

The HTTP Traffic Inspector has been removed. To delete any telemetry it stored earlier and stop its retention job, run [`supabase/remove-traffic-inspector.sql`](./supabase/remove-traffic-inspector.sql) once in the SQL Editor; it drops `ar_rahnu_traffic_events`, its functions and the `ar-rahnu-traffic-retention` cron job.

Each authenticated user can only read or modify their own row. App changes are saved automatically and updates from other sessions are received through Supabase Realtime.

SAG attachments are stored in the private `ar-rahnu-transaction-attachments` bucket; the portfolio JSON stores only their metadata and storage paths. Storage policies restrict access to the portfolio owner or an active organization Admin/Manager. The app creates short-lived signed URLs when a user opens an attachment.

Asset images use the same private bucket and access policies. Each asset can reference one JPEG, PNG or WebP image up to 5 MB; only metadata and the storage path are saved in the portfolio JSON. Replacing an image retains the previous file so audit snapshots and other references do not point to a deleted object. Duplicating an asset does not copy its image.

If an asset image upload reports **Bucket not found**, sign in to the correct Supabase project as its administrator, open SQL Editor and run the complete [`supabase/transaction-attachments.sql`](./supabase/transaction-attachments.sql) script. This creates the private bucket and its access policies together; creating a public bucket or a bucket without these policies is not sufficient. Then retry the upload. Running `schema.sql` alone does not create this bucket.

Profile photos are stored in the private `ar-rahnu-profile-photos` bucket under a folder named after the user's `auth.uid()`. Each member can upload, replace or remove one JPEG, PNG or WebP image up to 2 MB from Profil Saya → Butiran Peribadi & Alamat, and that is the single source of truth. The member directory **displays** the photo that already exists in the profile; when a member has no photo yet, an Admin can add one from Keahlian Ahli → Kemaskini Maklumat Ahli, which uploads the file and writes the same `avatar_photo_path`. Re-run [`supabase/profile-photos.sql`](./supabase/profile-photos.sql) after updating the app: the script now also grants organization Admins/Managers read/write/delete access to their members' avatar folders. The storage path is saved in the member's `avatar_photo_path` metadata (and mirrored in `memberRegistry.photoPath` as a cache), and the app renders a short-lived signed URL in the profile modal, the member directory and the header profile button. Replacing a photo deletes the previous file.

The member directory reads the storage folder `<uid>/avatar/` of each member instead of trusting the metadata alone, so a photo keeps appearing even when `avatar_photo_path` was never written (for example when the `user-admin` function has not been redeployed). The newest file in the folder wins, and the resolved path is cached for the session. Keahlian Ahli → **Semak Gambar Profil** opens an Admin-only scan that reports, per member, whether the file exists in storage and whether the metadata matches (`Ada gambar`, `Storan sahaja`, `Fail tiada`, `Tiada fail`, `Tidak dapat dibaca`). Running [`supabase/check-member-photos.sql`](./supabase/check-member-photos.sql) in the SQL Editor produces the same answer at database level, together with the list of files and the storage policies currently installed.

Every transaction, asset, institution and supplier record stores its own audit metadata: `createdBy`/`createdAt`, `updatedBy`/`updatedAt`, `lastAction` (`CREATE`, `UPDATE` or `DELETE`) and `recordType`. The record detail dialogs show who registered and who last changed the record. The same changes are written to the audit chain by the per-record trigger in [`supabase/audit-trail.sql`](./supabase/audit-trail.sql), so each event keeps the actor identity, the database timestamp, the record label/type and the list of changed fields even when a single save touches several records. Sign-in, sign-out, password changes, profile updates and exports are recorded through the `ar_rahnu_record_activity` RPC, and every member's activity lands in the organization chain so Admin/Manager accounts see one complete trail with actor, source IP, device and record reference. Client-side activity logging never blocks the user action: if the RPC is unavailable (migration not yet applied) the action still completes.

## Portfolio relationships and analytics

The app continues to save its portfolio JSON in `ar_rahnu_user_data` for compatibility. The portfolio-relations migration backfills that data into separate institution, supplier, asset and transaction tables. Foreign keys connect transactions to institutions and assets, and assets to suppliers. A database trigger keeps those related tables in sync whenever the portfolio JSON changes. The related tables are read-only to authenticated clients and use the same personal-portfolio or organization-manager access rules.

The original JSON remains the source of truth. If an old record points to an institution, asset or supplier that cannot be matched, the migration preserves the record and leaves that relationship unlinked rather than inventing a related record. The migration does not remove original JSON data.

The dashboard records one live gold-price snapshot per Malaysia calendar day, up to 365 days. Its 12-week price line is a linear trend based on at least seven snapshots, not a guaranteed market forecast or an external AI service. The overlap simulation uses the selected transaction's weight and redemption amount, the entered margin and fees, and the institution's saved spread. Positive balance means estimated cash surplus, not profit. The readiness score reflects maturity timing, available cash, EDT/EDR coverage and record completeness; it is not a credit or approval score.

Cash available, monthly income and expenses entered in the analytics page stay in browser storage, keyed to the signed-in account. They are not sent to Supabase or an AI provider, and are not shared across devices. Clearing browser storage removes them. The CSV analytics export includes portfolio records, snapshots and the current overlap scenarios, but not these local financial-readiness values.

## Surat Akuan Gadaian (SAG)

The Surat Akuan Gadaian module issues and prints the official financing letter. Its records are stored inside the same portfolio JSON under `sagDocuments`, and the letterhead/officer defaults are stored under `sagSettings`, so no new Supabase table, bucket or migration is required. Both keys are optional: portfolios saved before this module was added keep working, and the first SAG save adds the keys automatically.

Every letter is a snapshot that links to the rest of the portfolio:

- `transactionId` / `transactionRefNo` point to the Rekod SAG transaction that carries the financing amount, profit and maturity date. Selecting a transaction in the form pre-fills the institution, dates, values and marhun list, and the transaction row/detail dialog can open the related letter directly.
- `pledgeType` records the pledge transaction type of that letter (`Pajakan Asal`, `Salin`, `OL`, `Pusing`, `Tebus Cash`, `Tebus EDT`, `TS`, `TKS`, `US`, `Lelong`), taken from the linked transaction and editable in the form. `pledgeStatus` records the transaction status at the time the copy was saved. Every letter therefore states the type of pledge it was transacted under, and the module can filter by it.
- `previousDocumentNo` / `previousTransactionRefNo` record the earlier letter that was transacted to produce this one. When a follow-up transaction was created through the correction flow (OL/Pusing), the new letter links to its predecessor automatically; otherwise the form lets the user pick the earlier letter. The module's follow-up action opens the correction flow for the linked transaction, so the next letter is always transacted under its own pledge type.
- `member.userId` and `member.memberNo` point to the organization member registry. Name, MyKad and member number are copied from Keahlian Ahli, and the address, phone, heir and **No. Peti/Kotak Simpanan** entered on the letter are written back to that member's registry entry so the next letter can be filled automatically. That field is the box/peti number where the marhun is stored, as printed on the institution's receipt; it is optional, it is stored as `member.poBox`, the letter prints it on the official **No Kotak** row, and the letter prints `-` when it is empty. When the registry has no phone/address/heir for a member, the form asks the `user-admin` `get-member-profile` action (Admin only) and fills those fields from the member's own *Profil Saya* data, so a letter is never blank while the profile is complete. After redeploying `user-admin`, the `list` action also returns those fields, so the values arrive with the member list and no extra call is needed.
- `marhunItems[].assetId` points to the gold assets linked to the transaction. The form's "Pilih aset emas" picker lists the assets linked to the selected transaction first and then every asset in the Asset Record module, so a letter can pledge any recorded asset (EDT or EDR) even before a transaction is linked; each item stores the description, karat, appraised rate, weight and marhun value, and the header total is the sum of the items.
- `institutionId` / `institutionName` point to the institution used for the pledge.

The letter is a customer copy, not an issuer document: the app stores what the customer received from the institution. The letterhead holds the institution name, address and phone printed on that copy, while the officer and witness names are reference fields copied from the signature blocks of the physical letter and are never treated as app staff accounts.

The printed letter reproduces the paper form: customer and account block, the two tawarruq contracts, the profit schedule per payment period (calculated pro-rata by days between the financing and maturity dates), the marhun table, the seven customer declarations, and the customer/officer/witness signature blocks. Printing uses the browser print dialog (`Cetak / Simpan PDF`) on an A4 landscape-free layout; nothing is rendered on the server. Each letter carries a QR code and a short verification code derived from the document number, member number, MyKad hash, financing date and selling price, which lets an officer confirm that a printed copy matches the stored record without embedding the MyKad digits in the QR payload.

Letters are soft-deleted: `deletedAt` hides the record while the audit chain keeps the before/after snapshot. Status values are `Draf` (still editable), `Dikeluarkan` (issued and printed) and `Batal` (cancelled, printed with a watermark). Creating or editing a letter requires the `sag_create` permission; deleting requires `sag_delete` in the role matrix page. If the audit migration was installed before this module, re-run [`supabase/audit-trail.sql`](./supabase/audit-trail.sql) so SAG letters are included in the per-record audit trail.

## Audit trail and forensic limitations

The audit migration records database-observed changes to portfolio JSON, organization records, and membership/role/access records. The per-record trigger adds one event for each transaction, asset, institution and supplier created, updated or removed, with the record reference, jenis/kategori, and changed field names. The app also records sign-in, sign-out, password change, profile updates (personal, heir, bank, PDPA, avatar) and CSV/audit exports through the `ar_rahnu_record_activity` RPC; the actor is always taken from the session, and the RPC only accepts a fixed list of activity types so clients cannot forge record CRUD events. Every organization member's activity is written to the organization chain so Admin/Manager accounts see a single trail, while accounts without an organization membership keep a personal chain that only they can read. It retains before/after snapshots, SHA-256 snapshot hashes, actor/session/request metadata when Supabase supplies it, a database UTC timestamp, and a sequential SHA-256 chain. Audit rows cannot be changed through the authenticated API; the database trigger rejects ordinary `UPDATE` and `DELETE` operations, and deletes are only possible through the retention function. The Audit Trail page can verify the complete retained chain and export it as JSON. **Audit events are kept for 24 hours only**: `ar_rahnu_prune_audit_events()` removes older rows and is scheduled every 15 minutes with `pg_cron`; without `pg_cron`, run the function manually. Because the oldest events are deleted, verification starts from the earliest retained event and uses its stored `previous_hash` as the anchor; events pruned earlier cannot be re-verified, so export the JSON before the 24-hour window ends. The chain also does not backfill pre-migration history; events begin when the migration is installed.

**This is not yet a WORM archive or a court-certified forensic system.** A Supabase project owner or sufficiently privileged database operator can disable triggers, alter/truncate tables, and rebuild a chain. The Supabase database timestamp is not independently attested by an RFC 3161 Time-Stamp Authority. WORM storage and RFC 3161 integration have not been provisioned; the UI and export state these limitations. Before enabling an archive integration, select the WORM provider, retention duration and lock mode, a TSA endpoint and trust roots, a server-side delivery/retry policy, and an independent administrator for the archive. Store the archive credentials outside the browser and maintain verifiable, independently retained chain checkpoints. Do not describe the current database-only chain as immutable or independently time-certified.

The app's audit chain records application-level sign-in and sign-out, but it does not ingest Supabase Auth Audit Logs. Use Supabase's Auth Logs as the authoritative source for failed login attempts and other authentication events, and retain/export them separately until a server-side Auth log delivery integration is configured. IP and proxy headers depend on the Supabase request path and are attribution hints, not proof of actor identity; the browser does not provide a trustworthy hardware Device ID. The `x-audit-device-id` header is a locally generated identifier used to distinguish browsers, and the user agent is client-supplied. Before/after snapshots can contain portfolio data and must be protected according to the organization's privacy and retention requirements.
