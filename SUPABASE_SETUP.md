# Supabase setup

1. In the Supabase SQL Editor for project `zyikvjbnroicbeezpxvx`, run [`supabase/schema.sql`](./supabase/schema.sql). It creates the per-user data table, enables row-level security, and adds the table to Realtime.
2. Run [`supabase/audit-trail.sql`](./supabase/audit-trail.sql) in the same project to enable append-only, SHA-256 hash-chained records for portfolio, organization, and membership inserts, updates, and deletes. The file also installs a per-record trigger that writes one audit event for every transaction, asset, institution and supplier that is created, changed or removed, including the actor identity (`actor_user_id`, `actor_email`, `actor_display_name`), the database timestamp and the record label/type in `context`. Rerun the whole file after changes so the updated functions and triggers are installed. The Audit Trail page is available to Admin and Manager accounts. Redeploy the updated `user-admin` Edge Function as described in [`supabase/USER-MANAGEMENT.md`](./supabase/USER-MANAGEMENT.md) so administrative account actions include actor/session metadata and audit events.
3. Run [`supabase/traffic-inspector.sql`](./supabase/traffic-inspector.sql) to add seven-day HTTP telemetry storage and manager-only read access. Rerun it after changes to this file so updated database functions are installed. The migration attempts to schedule physical expiry every 15 minutes using `pg_cron`; if the extension is unavailable, expired rows are pruned on the next recorded request. Check the SQL Editor notices and enable `pg_cron` in Database → Extensions, then rerun the migration if scheduled deletion could not be installed.
4. Run [`supabase/portfolio-relations.sql`](./supabase/portfolio-relations.sql) to backfill relational records and install foreign keys and automatic synchronization. It must run after `schema.sql`.
5. Run [`supabase/transaction-attachments.sql`](./supabase/transaction-attachments.sql) to create the private bucket and access policies for SAG support documents. It must run after `schema.sql`. Each SAG accepts up to seven files, with a 50 MB limit per file.
6. Run [`supabase/profile-photos.sql`](./supabase/profile-photos.sql) to create the private bucket and access policies for member profile photos. Each user can only read, upload, replace and delete files inside their own `auth.uid()` folder.
7. Copy `.env.example` to `.env.local` and set `VITE_SUPABASE_ANON_KEY` to the project's publishable key (or legacy anon key). The project URL is already filled in. Never use a `service_role` or secret key in this browser app.
8. Restart the Vite server, open the app, and register/log in with Supabase Auth. If email confirmation is enabled, confirm the account before logging in.
9. The first login imports the existing browser's transactions, institutions, assets and suppliers only when that account has no cloud data yet. If cloud data already exists, it is loaded as the source of truth.

Each authenticated user can only read or modify their own row. App changes are saved automatically and updates from other sessions are received through Supabase Realtime.

SAG attachments are stored in the private `ar-rahnu-transaction-attachments` bucket; the portfolio JSON stores only their metadata and storage paths. Storage policies restrict access to the portfolio owner or an active organization Admin/Manager. The app creates short-lived signed URLs when a user opens an attachment.

Asset images use the same private bucket and access policies. Each asset can reference one JPEG, PNG or WebP image up to 5 MB; only metadata and the storage path are saved in the portfolio JSON. Replacing an image retains the previous file so audit snapshots and other references do not point to a deleted object. Duplicating an asset does not copy its image.

If an asset image upload reports **Bucket not found**, sign in to the correct Supabase project as its administrator, open SQL Editor and run the complete [`supabase/transaction-attachments.sql`](./supabase/transaction-attachments.sql) script. This creates the private bucket and its access policies together; creating a public bucket or a bucket without these policies is not sufficient. Then retry the upload. Running `schema.sql` alone does not create this bucket.

Profile photos are stored in the private `ar-rahnu-profile-photos` bucket under a folder named after the user's `auth.uid()`. Each member can upload, replace or remove one JPEG, PNG or WebP image up to 2 MB from Profil Saya → Butiran Peribadi & Alamat. The storage path is saved in the user's `avatar_photo_path` auth metadata, and the app renders a short-lived signed URL in the profile modal and the header profile button. Replacing a photo deletes the previous file.

Every transaction, asset, institution and supplier record stores its own audit metadata: `createdBy`/`createdAt`, `updatedBy`/`updatedAt`, `lastAction` (`CREATE`, `UPDATE` or `DELETE`) and `recordType`. The record detail dialogs show who registered and who last changed the record. The same changes are written to the audit chain by the per-record trigger in [`supabase/audit-trail.sql`](./supabase/audit-trail.sql), so each event keeps the actor identity, the database timestamp and the record label/type even when a single save touches several records.

## Portfolio relationships and analytics

The app continues to save its portfolio JSON in `ar_rahnu_user_data` for compatibility. The portfolio-relations migration backfills that data into separate institution, supplier, asset and transaction tables. Foreign keys connect transactions to institutions and assets, and assets to suppliers. A database trigger keeps those related tables in sync whenever the portfolio JSON changes. The related tables are read-only to authenticated clients and use the same personal-portfolio or organization-manager access rules.

The original JSON remains the source of truth. If an old record points to an institution, asset or supplier that cannot be matched, the migration preserves the record and leaves that relationship unlinked rather than inventing a related record. The migration does not remove original JSON data.

The dashboard records one live gold-price snapshot per Malaysia calendar day, up to 365 days. Its 12-week price line is a linear trend based on at least seven snapshots, not a guaranteed market forecast or an external AI service. The overlap simulation uses the selected transaction's weight and redemption amount, the entered margin and fees, and the institution's saved spread. Positive balance means estimated cash surplus, not profit. The readiness score reflects maturity timing, available cash, EDT/EDR coverage and record completeness; it is not a credit or approval score.

Cash available, monthly income and expenses entered in the analytics page stay in browser storage, keyed to the signed-in account. They are not sent to Supabase or an AI provider, and are not shared across devices. Clearing browser storage removes them. The CSV analytics export includes portfolio records, snapshots and the current overlap scenarios, but not these local financial-readiness values.

## Audit trail and forensic limitations

The audit migration records database-observed changes to portfolio JSON, organization records, and membership/role/access records. It retains before/after snapshots, SHA-256 snapshot hashes, actor/session/request metadata when Supabase supplies it, a database UTC timestamp, and a sequential SHA-256 chain. Audit rows cannot be changed through the authenticated API; the database trigger rejects ordinary `UPDATE` and `DELETE` operations. The Audit Trail page can verify the complete visible chain and export it as JSON. It does not backfill pre-migration history; events begin when the migration is installed.

**This is not yet a WORM archive or a court-certified forensic system.** A Supabase project owner or sufficiently privileged database operator can disable triggers, alter/truncate tables, and rebuild a chain. The Supabase database timestamp is not independently attested by an RFC 3161 Time-Stamp Authority. WORM storage and RFC 3161 integration have not been provisioned; the UI and export state these limitations. Before enabling an archive integration, select the WORM provider, retention duration and lock mode, a TSA endpoint and trust roots, a server-side delivery/retry policy, and an independent administrator for the archive. Store the archive credentials outside the browser and maintain verifiable, independently retained chain checkpoints. Do not describe the current database-only chain as immutable or independently time-certified.

The app's audit chain does not ingest Supabase Auth Audit Logs. Use Supabase's Auth Logs as the authoritative source for login/logout and authentication events, and retain/export them separately until a server-side Auth log delivery integration is configured. IP and proxy headers depend on the Supabase request path and are attribution hints, not proof of actor identity; the browser does not provide a trustworthy hardware Device ID. Before/after snapshots can contain portfolio data and must be protected according to the organization's privacy and retention requirements.

## Traffic Inspector

The Traffic Inspector is separate from the forensic hash chain. It records browser-observed outbound Supabase HTTP calls only; it cannot inspect incoming static-site requests, TCP connections, or requests to unrelated external services. It records metadata and bounded JSON request/response bodies, omits Supabase Auth endpoint bodies, and redacts common credential/contact fields. Remaining bodies can still contain sensitive financial data. All active organization members can contribute events; only Admins and Managers can view the organization feed. Each browser can pause its own capture, and events are retained for seven days then deleted. The client-observed duration/status and proxy-provided IP are diagnostic hints, not independently verified evidence. No external archive is configured.
