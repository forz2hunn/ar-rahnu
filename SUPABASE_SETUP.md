# Supabase setup

1. In the Supabase SQL Editor for project `zyikvjbnroicbeezpxvx`, run [`supabase/schema.sql`](./supabase/schema.sql). It creates the per-user data table, enables row-level security, and adds the table to Realtime.
2. Run [`supabase/audit-trail.sql`](./supabase/audit-trail.sql) in the same project to enable append-only, SHA-256 hash-chained records for portfolio, organization, and membership inserts, updates, and deletes. The Audit Trail page is available to Admin and Manager accounts. Redeploy the updated `user-admin` Edge Function as described in [`supabase/USER-MANAGEMENT.md`](./supabase/USER-MANAGEMENT.md) so administrative account actions include actor/session metadata and audit events.
3. Run [`supabase/traffic-inspector.sql`](./supabase/traffic-inspector.sql) to add seven-day HTTP telemetry storage and manager-only read access. The migration attempts to schedule physical expiry every 15 minutes using `pg_cron`; if the extension is unavailable, expired rows are pruned on the next recorded request. Check the SQL Editor notices and enable `pg_cron` in Database → Extensions, then rerun the migration if scheduled deletion could not be installed.
4. Copy `.env.example` to `.env.local` and set `VITE_SUPABASE_ANON_KEY` to the project's publishable key (or legacy anon key). The project URL is already filled in. Never use a `service_role` or secret key in this browser app.
5. Restart the Vite server, open the app, and register/log in with Supabase Auth. If email confirmation is enabled, confirm the account before logging in.
6. The first login imports the existing browser's transactions, institutions, assets and suppliers only when that account has no cloud data yet. If cloud data already exists, it is loaded as the source of truth.

Each authenticated user can only read or modify their own row. App changes are saved automatically and updates from other sessions are received through Supabase Realtime.

## Audit trail and forensic limitations

The audit migration records database-observed changes to portfolio JSON, organization records, and membership/role/access records. It retains before/after snapshots, SHA-256 snapshot hashes, actor/session/request metadata when Supabase supplies it, a database UTC timestamp, and a sequential SHA-256 chain. Audit rows cannot be changed through the authenticated API; the database trigger rejects ordinary `UPDATE` and `DELETE` operations. The Audit Trail page can verify the complete visible chain and export it as JSON. It does not backfill pre-migration history; events begin when the migration is installed.

**This is not yet a WORM archive or a court-certified forensic system.** A Supabase project owner or sufficiently privileged database operator can disable triggers, alter/truncate tables, and rebuild a chain. The Supabase database timestamp is not independently attested by an RFC 3161 Time-Stamp Authority. WORM storage and RFC 3161 integration have not been provisioned; the UI and export state these limitations. Before enabling an archive integration, select the WORM provider, retention duration and lock mode, a TSA endpoint and trust roots, a server-side delivery/retry policy, and an independent administrator for the archive. Store the archive credentials outside the browser and maintain verifiable, independently retained chain checkpoints. Do not describe the current database-only chain as immutable or independently time-certified.

The app's audit chain does not ingest Supabase Auth Audit Logs. Use Supabase's Auth Logs as the authoritative source for login/logout and authentication events, and retain/export them separately until a server-side Auth log delivery integration is configured. IP and proxy headers depend on the Supabase request path and are attribution hints, not proof of actor identity; the browser does not provide a trustworthy hardware Device ID. Before/after snapshots can contain portfolio data and must be protected according to the organization's privacy and retention requirements.

## Traffic Inspector

The Traffic Inspector is separate from the forensic hash chain. It records browser-observed outbound Supabase HTTP calls only; it cannot inspect incoming static-site requests, TCP connections, or requests to unrelated external services. It records metadata and bounded JSON request/response bodies, omits Supabase Auth endpoint bodies, and redacts common credential/contact fields. Remaining bodies can still contain sensitive financial data. All active organization members can contribute events; only Admins and Managers can view the organization feed. Each browser can pause its own capture, and events are retained for seven days then deleted. The client-observed duration/status and proxy-provided IP are diagnostic hints, not independently verified evidence. No external archive is configured.
